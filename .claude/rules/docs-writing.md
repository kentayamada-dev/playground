## ルールや手順を書くとき

- 書き方や形式が文だけでは伝わりにくいルールには、例を添える
- 例は実際に動かして確認したものだけを載せる。確認できないものは載せないか、「未確認」と明記する
- 例が 1 つだと、その場面にしか当てはまらないと読まれやすいので、場面の違う例を並べるか、当てはまる範囲を文で補う

## 疎結合に書く

- ほかのツール・スキル・ファイルの名前や場所は、なくても伝わるなら書かない
- 例は、どのファイルのどこから取ったかを示さず、それだけで読める形にする

## README の書き方

内容ごとに、書く場所を次の表で決める。

| 内容 | 書く場所 |
| - | - |
| 使い方と挙動（何をするか・何を対象にするか・どう操作するか） | README |
| 1 か所の設定やコードに結びつく理由 | その設定やコードのコメント |
| その行を編集する人だけが要る手順 | その行のコメント |
| 複数の箇所にまたがる理由と、JSON などコメントを書けないファイルの理由 | README |
| 使う人と編集する人の両方が要る内容 | README とコメントの両方 |

理由をコメントに書いたときは、必要に応じて README で「理由は〜のコメントに書いている」と案内する。

次のように分ける。

- 書く:「`429`・`502`・`503`・`504` は成功として扱う」（挙動）
- 書かない:「レート制限の `429` は、リンク切れとは限らないため」（理由。コメントにある）
- 書かない:「`USER_NAME` を変えるときは、両方の `devcontainer.json` の `remoteUser` も合わせる」（編集する人向け。コメントにある）
- 書く:「版は nodejs の Dockerfile だけで管理し、Renovate が更新する」（pnpm の版。使う人と編集する人の両方が要る）
- 書く: mise の設定を `.github` に置く理由（複数のワークフローにまたがり、1 か所のコードに結びつかない）

## 版の番号

- いま使っている依存の版の番号は、文書に書かない
- 版のタグで固定した根拠のリンクや、PR のタイトルの例のように、ある時点の版を示すものは書いてよい

次のように分ける。

- 書かない:「`node`（Node.js 26）」
- 書かない:「pnpm 12 は、1 つ目の文書に pnpm 本体の版を書く」（「pnpm は」とする）
- 書く: `blob/v2.102.0/` のように、版のタグで固定した根拠のリンク

## CI の検査に通る書き方

- `.md` はすべて CI で文章と書式を検査される
- 1 文を 100 文字以内にし、表記は `.github/textlint/prh.yml` に合わせる
