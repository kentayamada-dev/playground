リポジトリのすべてのコメントを、CONTRIBUTING.md の「コメント」の規約で精査する。
おもな目的は、変わらないまま古くなったコメントを見つけること。こうしたコメントは、差分の確認では見つからない。たとえば次のものがある。

- Renovate が依存の版を上げても、コメントにある根拠のリンクの版は上がらない
- 外部のツールやレジストリが変わると、コメントの前提が崩れる
- 実行ログのように、期限が来ると根拠が読めなくなる

起動後は、手順 4 の報告まで確認を挟まずに進めてよい。ファイルは、手順 5 でユーザーが選んだ範囲だけを直す。

## 1. 対象を集める

1. `git ls-files` で、コメントを書けるファイルの一覧を作る。コメントの書き方（`#`・`//`・`<!-- -->`）は、ファイルの種類ごとに違う
2. 次のものは対象から外す
   - ロックファイルと、ツールが書き出すファイル（`go.sum`・`pnpm-lock.yaml` など）
   - ツールへの指示（`# renovate:`・`// indirect`・`textlint-disable` など）。ただし、`shellcheck disable` の後ろに書いた理由は対象にする
   - ヒアドキュメントやテストの入力として書いた文字列
   - PR と issue のテンプレートにある記入のガイド
3. コメントだけでなく、コメントが説明するコードも読む。同じコメントが複数のファイルにあるときは、ファイルごとにコードと合うかを確認する

## 2. 規約を当てる

CONTRIBUTING.md の「コメント」を読み、各コメントに当てる。次のものは見落としやすい。

- ほかのファイルから写したコメント: 写した先のトリガー・対象・設定の値と合っているか
- 書き写し: ほかの箇所の値の列挙、「ここから下は」のような位置、「〜と同じく」のような比較
- 根拠のリンク: ブランチを指すリンク、実行ログの URL、版のずれ（手順 3）
- コードの言い換え: 数行しかないコードの要約

## 3. 根拠のリンクの版を確認する

版のタグやコミットで固定したリンクは、今使っている版と比べる。今使っている版は、`.github/mise.toml`・`uses:` の行末のコメント・ロックファイル・`go.mod`・Dockerfile の `FROM` などで調べる。

- 版がずれていたら、両方の版のソースを取得して読み比べ、主張が今の版でも成り立つかを確認する
  - ソースは `curl -fsSL https://raw.githubusercontent.com/<owner>/<repo>/<タグ>/<パス>` か、`gh api -H 'Accept: application/vnd.github.raw' 'repos/<owner>/<repo>/contents/<パス>?ref=<タグ>'` で取得する
  - 成り立てば、URL の版と行番号を今の版に替える
  - 成り立たなければ、URL を替えずに報告する。コメントだけでなく、コードや設定の見直しが要るため
- 過去に起きた実例を示すリンクは、版を上げない。実例だとわかる書き方になっているかを確認する
- ブランチを指すリンクは、中身が主張と合うことを確認してから、今のコミットに固定する
- 実行ログの URL は、その実行を記録した PR のリンクに替える。URL を足したコミットは `git log -S '<実行の ID>'` で探す。その PR の本文に、実行の記録があるかを確認する
- コメントが前提にしている外部の状態（レジストリの定義、新しい版のリリースなど）が変わっていないかも、確認できる範囲で確認する

## 4. 量を測って報告する

1. コメント行の割合、4 行以上続くコメントのかたまりの数、いちばん長いかたまりの行数を測る。前回の精査の PR があれば、その数と比べる。比べられるよう、数え方もあわせて伝える
2. 見つけたものを次の分類に分け、それぞれ `path:行番号`・問題・直し方の案・根拠をそろえて報告する
   - すでに事実と合わない
   - 古くなりやすい、置き場所が違う
   - 根拠の版のずれ
   - コードの言い換え
   - 判断が分かれる（残してもよい）
3. 確認していないことは「未確認」、根拠から組み立てた見立ては「推測」と書く。外部の仕様についての主張を、どこまで確認したかも伝える

## 5. 直す範囲を選ばせて直す

1. 分類ごとに直すかを `AskUserQuestion` で選ばせる。設定の値を変えるなど、動作が変わる直し方は別の問いにして候補を示す
2. `main` にいるなら、CONTRIBUTING.md の規約で作業ブランチを切ってから直す
3. 選ばれた範囲だけを直し、変えた箇所と確認した結果を伝える。コミットや PR の作成は、ユーザーに頼まれるまで始めない
