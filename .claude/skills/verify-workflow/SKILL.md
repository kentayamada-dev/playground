---
name: verify-workflow
description: GitHub Actionsのワークフロー（.github/workflows配下）を作成・変更したときに、その動作を実際のCIで検証する。ワークフローを作る・変える作業をしたら使う。ワークフロー以外の変更では使わない
---

ワークフローの変更を、実際の GitHub Actions で動かして検証する。YAML の構文チェックやローカルでの再現だけで検証を終えない。

指示がないのにコミットや push を始めてはいけない。検証用ブランチの push や PR の作成、リポジトリ設定の一時的な変更は、手順 2 で計画の承認を得てから始める。

## 1. 検証項目を洗い出す

変更したワークフローを読み、次の観点で確かめることを列挙する。

- 分岐の両側: `if` や `paths` などの条件ごとに、実行されるケースと飛ばされるケースの両方
- フィルタの境界: 変更したファイルで分岐するなら、リネーム・削除・設定ファイルだけの変更・ドットで始まるディレクトリのファイルが意図どおりに一致するか
- 失敗時の素通り: 判定や前処理のステップが失敗したときに、ジョブも失敗して必須チェックを通らないこと
- イベント: `on` に書いたイベントごと（`pull_request`・`push` など）。同じ PR への追加の push（`synchronize`）も含める
- `workflow_dispatch`: ワークフローがデフォルトブランチに無いと起動できない。新しく作るワークフローなら、マージ後に確かめる
- `schedule`: デフォルトブランチでしか動かない。ジョブの中身は、`workflow_dispatch` も設定してあればマージ後に手動で動かして確かめる。定期実行の起動は、次の実行時刻を過ぎてから確かめる
- 失敗すべきケース: 検査用のジョブなら、違反を入れたときにジョブが失敗すること
- 必須チェックとの組み合わせ: 必須チェックに入るジョブなら、条件で飛ばしたときもマージできること。失敗したときにマージできないこと
- 権限: ログの `GITHUB_TOKEN Permissions` の欄が `permissions` の指定どおりで、足りない権限が無いこと
- キャッシュ: キャッシュを使うなら、ログで復元と保存の結果、キーの値を確かめる
- 外部のアクション: ログの `Download action repository` の行で、実際に使われたバージョンと SHA を記録する
- マージ後にしか確かめられないもの: デフォルトブランチへの push や、デフォルトブランチのキャッシュなど
- 確かめる手段が無いもの: フォークからの PR など

## 2. 検証計画の承認を得る

検証項目ごとに、検証用ブランチと PR・一時的な設定・期待する結果をまとめる。それを `AskUserQuestion` で示して承認を得る。マージ後に確かめるものと、確かめられないものもあわせて伝える。

## 3. 実際の CI で動かす

- 検証用ブランチは、作業ブランチから `test/<内容>` の名前で切る
- 検証用の PR の base には作業ブランチを指定する。検証用の PR はマージしない
- 失敗させる内容（違反を含むファイルなど）と、飛ばさせる内容は、別々の PR に分ける。フィルタの境界のケースもケースごとに分ける
- 失敗時の素通りは、判定や前処理のステップを検証用の PR で一時的に失敗させて確かめる（`run` に `exit 1` を足すなど）
- `synchronize` は、検証用の PR にもう 1 回 push して確かめる
- `push` イベントは、検証用ブランチを `on.push.branches` に加えたワークフローで確かめる。そのワークフローを検証用ブランチに push する
- `workflow_dispatch` は、`gh workflow run <ワークフロー> --ref <ブランチ>` で動かす。デフォルトブランチにあるワークフローだけが対象になる
- 必須チェックとの組み合わせは、検証用ブランチだけを対象にした一時的なルールセットを `gh api` で作って確かめる。ルールセットは、対象のブランチを push してから作る
- マージ状態は、CI の実行中と終了後の両方で記録する
- CI の終了は `gh pr checks <番号> --watch` や `gh run watch <run_id>` で待つ

## 4. 根拠を取る

CI の成否だけで結論を出さない。検証項目ごとに、次のどれかを根拠にする。

- ステップごとの結果: `gh api repos/<owner>/<repo>/actions/jobs/<job_id>` の `steps[].conclusion`
- ジョブのログ: `gh run view <run_id> --job <job_id> --log`。権限・キャッシュ・アクションのバージョンもここで確かめる
- チェックの報告元: `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` の名前と app id
- マージ状態: `gh pr view <番号> --json mergeStateStatus,statusCheckRollup`

期待と違う結果が出たら、検証を続けずにユーザーへ報告する。

## 5. 後片付けをする

- 検証用の PR は `gh pr close <番号> --delete-branch` で閉じ、ブランチを削除する
- 一時的なルールセットは `gh api -X DELETE repos/<owner>/<repo>/rulesets/<id>` で削除する
- `gh api repos/<owner>/<repo>/rulesets` で、一時的なルールセットが残っていないことを確かめる
- `git ls-remote --heads origin 'test/*'` で、検証用ブランチが残っていないことを確かめる
- 作業ブランチに戻り、`git status -sb` で未コミットの変更が無いことを確かめる

## 6. 結果を PR 本文に書く

作業ブランチの PR 本文に、検証項目ごとの結果を書く。本文の書き換えは、create-pr スキルの「更新」の手順に従う。

- 「確認方法」には、検証用の PR の番号と run のリンク、根拠にした出力を書く
- 確かめられないものは「レビューで見てほしい点」に未確認と書く。推測で補った部分は推測と明記する
- マージ後に確かめるものは、マージ後に同じ手順で確かめ、結果を本文に反映する
